# Урок 5. EquiHist — учиться на ответах запросов, а не на данных

**Ветка:** `lesson/05-equi-hist` (от `lesson/04-entropy-hist`)
**Пишешь:** `estimators/equi_hist.py`
**Тесты:** `tests/lessons/test_05_equi_hist.py`
**Эталон:** `dev:models/equi_hist.py` (`EquiHistLearner`)
**Время:** 1–2 часа

---

## Зачем

До сих пор все методы строились по выборке — один раз, «до запросов». Но СУБД после выполнения
запроса **знает точный ответ**. Это бесплатный сигнал: если оценка была 100, а пришло 400,
счётчики бакетов можно подправить. Так работают self-tuning гистограммы (LEO в DB2, STHoles,
ST-histogram из урока 6). EquiHist — самый простой вариант этой идеи и мостик к уроку 6.

Протокол **prequential**: на каждый запрос сначала `predict` (это и есть оценка, которую
мы мерим), потом `observe(q, actual)`. Модель никогда не видит ответ до своей оценки.

## Теория

Старт — обычный Equi-Width по выборке. На каждый ответ:

```
ratio = clip(actual / pred, 0.1, 10)
для каждого бакета, перекрытого запросом:
    frac  = overlap / width
    count = max(1, count · ratio^(lr · frac))        # lr = 0.5
```

- мультипликативное обновление — потому что q-error мультипликативен;
- степень `lr · frac`: бакет, покрытый целиком, двигается сильнее, задетый краем — слабее;
- `clip` — защита от взрыва на одном странном запросе;
- `count ≥ 1` — бакет не «умирает» навсегда (иначе `pred = 0` и учиться нечем).

Важно: фидбэк размазывает ошибку **по всем перекрытым бакетам одинаково** (в степени доли
перекрытия) — модель не знает, какой из бакетов на самом деле виноват.

## Что написать

```python
def build(sample, mn, mx, total_rows, n_buckets, learning_rate=0.5) -> "EquiHist": ...
    def observe(self, q, actual) -> None
```

Переиспользуй Equi-Width из урока 1 (наследование или композиция). Требование к скорости:
`observe` трогает **только перекрытые бакеты** (через `searchsorted` или арифметику индексов)
и обновляет префиксные суммы. 200k запросов должны проходить за секунды.

## Ловушки

- **Эталон медленный**: `EquiHistLearner.update` перебирает **все** бакеты на каждый запрос и
  сбрасывает кэш (`self.b_lo = None`), из-за чего следующий `predict` заново строит массивы —
  O(B) на запрос. Именно поэтому EquiHist выкинули из дизайна эксперимента «как слишком
  медленный». Это не свойство метода, это свойство реализации. Твоя должна быть быстрой.
- Обновлять счётчики, но забыть префиксные суммы — `predict` будет читать старые.
- `pred == 0` → `ratio` не определён: пропусти обновление.

## Поиграть

1. Нарисуй скользящую медиану q-error по номеру запроса (окно 5 000) на `uniform`, `sparse_cluster`
   и `dsb/cr_item_sk`. Как быстро модель сходится? Сходится ли вообще?
2. `learning_rate` = 0.1, 0.5, 1.0. Где компромисс «скорость / стабильность»?
3. **Почему на `dsb/cr_item_sk` медиана стала хуже Equi-Width** (1.099 против 1.021)?
   Подсказка: в DSB ~1 400 уникальных запросов повторяются сотни раз, а в бакетах — пики.
   Что делает обновление, когда два частых запроса в одном бакете «тянут» его count в разные стороны?
4. Почему на `uniform` EquiHist лучше любого сэмплового метода (1.004)? С чем это совпадает из урока 0?

## Итог урока → `lessons/notes/05.md`

Плюсы: учится на точных ответах и убирает шум выборки; тривиальная реализация.
Минусы: не может исправить форму внутри бакета (только массу); ошибку делит между бакетами вслепую;
конфликтующие запросы в одном бакете раскачивают счётчик; нужен поток точных ответов.
