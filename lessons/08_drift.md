## Зачем

Статистика строится в момент ANALYZE, а данные потом меняются. Вопрос второй половины
диссертации: **что происходит с оценками, когда данные дрейфуют, и сколько стоит их вернуть?**
Прежде чем адаптировать Hybrid (урок 9), нужно честно поставить эксперимент для всех
бейзлайнов — иначе сравнивать не с чем. Половина ошибок в старых drift-результатах была
ошибками протокола, а не методов.

## Теория

### Сценарии (`data/generated/60000000_hard/`)

| сценарий | каталог | что происходит |
|---|---|---|
| `replace` (по умолчанию) | `shift_normal_to_zipf_5%` | за 20 шагов по 5% строки `normal` **заменяются** на `zipf`; N постоянно |
| `add` | `shift_normal_to_zipf_5%_dataset` | `zipf` **добавляется** к `normal`; N растёт 60M → 120M |

Каждый шаг — `step_N.pkl` (6 полей: `mn, mx, N, freq, sample, k`) и свой ворклоад «по данным
шага» — запросы смещаются вслед за данными.

### Что каждый метод делает на новом шаге

| метод | реакция | что меняется |
|---|---|---|
| Equi-Width, EquiHist | `refresh` = ANALYZE: счётчики по новой выборке | **сетка — с шага 0** |
| TKHist | пересборка по новой выборке на сетке шага 0 | счётчики + top-k |
| EquiDepth, EntropyHist | полная пересборка | **новые границы** |
| STHist | не видит данных; учится только на ответах | всё — через фидбэк |
| Hybrid (урок 9) | ANALYZE счётчиков + FT + RB | счётчики, массы, модели; сетка — с шага 0 |

### Протокол стенда (`check_drift.py`) — одинаковый для всех

1. Шаг 0: `build` по выборке шага 0.
2. Шаг `s > 0`: `refresh(sample_s, mn, mx, N)`, если метод это умеет (время → `refresh_s`).
3. **shock** — оценка на **нечётных** запросах шага: «как модель встречает новые данные».
4. **Фидбэк** — только с **чётных** запросов: `observe` по одному или `adapt` пачкой.
5. **adapted** — снова нечётные. Запросы, на которых модель училась, в оценку **не попадают**.

Пункт 5 — отличие от старых раннеров: там FT/RB Hybrid оценивались на тех же запросах, что
пришли в фидбэк (in-sample), а STHist — prequential. Здесь все методы в одинаковых условиях.

## Что написать

`refresh(self, sample, mn, mx, total_rows)` для каждого сэмплового метода, по таблице выше.
`STHist` — без `refresh` (он и не должен видеть выборку); опционально обновить `T` из каталога.

## Ловушки

- **Главный баг старых результатов.** `run_equiwidth_drift.py` пересчитывал `b.count`, но не
  вызывал `_bake_vectorized_data()`, а `predict` читает закэшированные `b_count / prefix_counts`.
  Equi-Width всё время отвечал по данным шага 0 и «взрывался» до q-error 1 685 — это был замер
  гистограммы **без ANALYZE**. `test_refresh_follows_new_sample` ловит ровно это.
- Значения выборки вне сетки шага 0 (`mx` шага может быть больше) — прижать к краям.
- Новая выборка — новое `N`: масштаб `N_s / len(sample_s)`, а не старый.
- `refresh` меряем отдельно от оценки — это «цена ANALYZE», её сравнивают с ценой адаптации Hybrid.

## Поиграть

1. **Контроль «без ANALYZE»:** временно сделай `refresh` пустым у Equi-Width. Это и есть старый
   баг — посмотри, как он выглядит в цифрах.
2. **Equi-Width с новой сеткой:** `refresh` строит гистограмму заново, с `k` нового шага (FD
   для zipf — 2000 бакетов). Насколько это ближе к EquiDepth? Что тогда остаётся от разницы
   «фиксированная сетка vs новые границы»?
3. Почему у Equi-Width растёт хвост (2.6 → 20.5), если счётчики каждый шаг свежие?
   (Подсказка: где оказывается вся масса `zipf` относительно бакетов сетки `normal`?)
4. Сценарий `add`: кто теперь лучший и почему мягкий дрейф меняет картину?

## Вопросы для самопроверки

1. Что именно «устаревает» у каждого метода под дрейфом: счётчики, границы, форма?
2. Почему EquiDepth и EntropyHist в конце почти идеальны, а Equi-Width — худший, хотя все трое
   делают ANALYZE на каждом шаге?
3. Почему оценивать адаптацию на тех же запросах, на которых модель училась, — нечестно?
4. Сколько стоит ANALYZE у каждого метода и что это значит для частоты его запуска в СУБД?
