## Зачем

Equi-Width — самая простая гистограмма и **нижняя планка эксперимента** («то, что есть в любой
СУБД»). Но важнее другое: все остальные методы — это Equi-Width, у которого заменили одну
деталь. TKHist добавляет точные частые значения, EquiDepth и EntropyHist двигают границы,
EquiHist и STHist учат счётчики по фидбэку, Hybrid меняет предположение внутри бакета.
Если этот урок понятен до конца, остальные — вариации.

## Теория

### Построение

1. Ширина бакета `bw = ceil((mx - mn + 1) / k)`. Бакеты `[mn, mn+bw-1], [mn+bw, ...]`;
   **последний может быть уже** — он обрезан по `mx`.
2. Счётчик бакета = (число точек выборки в бакете) × `N / len(sample)`.
   Быстро: отсортировать выборку один раз, дальше `searchsorted(lo, "left")` и
   `searchsorted(hi, "right")` на бакет.

### Оценка запроса `[a, b]`

```
         запрос [a ─────────────────────── b]
бакеты: [  B_s  ][  B_s+1 ] ... [  B_e-1 ][  B_e  ]
          край      целиком       целиком    край
```

- индексы краевых бакетов — **O(1)** арифметикой: `s = (a - mn) // bw`, `e = (b - mn) // bw`
  (обрезать до `[0, n-1]`) — потому что все бакеты одной ширины;
- внутренние бакеты `s+1 .. e-1` — сумма счётчиков, O(1) через **префиксные суммы счётчиков**;
- краевые — **предположение равномерности**: доля строк = доля покрытой ширины,
  `overlap / width_i * count_i`. Делить на ширину **этого** бакета, а не `bw` (последний уже).

Вся ошибка Equi-Width — в двух краевых бакетах. Отсюда главный вывод курса:

> **Узкий запрос** почти целиком состоит из краёв → качество определяется тем, насколько метод
> понимает, что происходит **внутри** бакета. **Широкий** — в основном целые бакеты, ошибки
> краёв тонут в сумме, и все методы выглядят одинаково.

### Два источника ошибки

| источник | что это | как уменьшить |
|---|---|---|
| **форма** (bias) | внутри бакета данные не равномерны | больше бакетов (уже), или модель формы (Hybrid) |
| **шум выборки** (variance) | в бакете мало точек выборки → счётчик неточен | меньше бакетов (шире) |

Это компромисс: уже бакет → меньше ошибка формы, но меньше точек выборки на бакет и больше шум.
Фридман–Диаконис — эвристика, выбирающая середину.

## Что написать

```python
def build(sample, mn, mx, total_rows, n_buckets) -> "EquiWidth": ...

class EquiWidth:
    bucket_ranges            # [(lo, hi), ...]
    def predict(self, q) -> float
    def n_floats(self) -> int   # n_buckets + 2 (mn и ширина задают всю сетку)
```

Совет по структуре, который окупится в уроках 2, 5, 7, 8: держи бакеты в **numpy-массивах**
`lo, hi, width, count, prefix` и отдельную функцию `_bake()`, которая пересчитывает `prefix`
из `count`. Любое изменение `count` — и `_bake()` обязательно (см. урок 8: ровно эту ошибку
нашли в `run_equiwidth_drift.py`).

## Ловушки

- **Последний бакет уже остальных.** Тест `test_last_bucket_can_be_narrower` ловит деление на `bw`.
- **Целочисленный счётчик.** Эталон делает `int(count * scale)` — разница ничтожна, но точечные
  тесты могут разойтись в 6-м знаке. Храни `float`.
- **Точечный запрос `[v, v]`**: `overlap = 1`, а не 0.
- **Запрос, целиком попавший в один бакет** (`s == e`) — не считать его дважды как «левый край»
  и «правый край».

   `build` параметр `scale=1.0` (`n_buckets = int(n_buckets * scale)`) и запусти
