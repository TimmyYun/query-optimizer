## Зачем

Первая «починка» Equi-Width. Самый частый случай, когда равномерность внутри бакета ломается, —
**одно-два очень частых значения** («горячий товар», дефолтная дата, `0`). Если хранить их
счётчики точно, остаток бакета гораздо ближе к равномерному. Та же идея лежит в MCV-списке
PostgreSQL (урок 3) — здесь она в чистом виде.

## Теория

Каждый бакет equi-width хранит:
- `count` — сколько строк в бакете (как в Equi-Width);
- `top_k` — словарь `{значение: count}` для `k` самых частых значений бакета **по выборке**;
- `resid = count − Σ top_k` — остаток, он считается равномерным по ширине бакета.

Оценка запроса:
- **целиком покрытые бакеты** — полный `count` (top-k уже внутри него);
- **краевой бакет** — `overlap / width * resid` **+** сумма top-k значений, попавших в запрос.

Дополнительно, как в оригинале: если различных значений в выборке меньше `n_categorical = 200`,
колонка считается категориальной и **все** значения хранятся точно.

При `top_k = 0` это ровно Equi-Width — хорошая проверка (тест `test_topk_zero_is_equi_width`).

### Почему это помогает именно на DSB

`cr_item_sk` — «горячие товары»: 1% значений даёт 52% строк. Запрос, попавший на горячее
значение, Equi-Width размазывает по всему бакету, TKHist отвечает точно. На синтетике
`normal` пиков нет — там выигрыш маленький.

## Что написать

```python
def build(sample, mn, mx, total_rows, n_buckets, top_k=5, n_categorical=200) -> "TKHist": ...
```

Шаги:
1. Сетка — как в Equi-Width (переиспользуй код урока 1).
2. `values, counts = np.unique(sample, return_counts=True)` — один раз.
3. Номер бакета каждого различного значения: `(values - mn) // bw`; границы в отсортированном
   `values` — `searchsorted(bucket_idx, arange(n+1))`. Так все бакеты обрабатываются без цикла
   по выборке.
4. В каждом бакете — `argsort(-counts, kind="stable")[:top_k]` (при равенстве — меньшее значение).
5. `predict` — как в Equi-Width, но краевой бакет считается через `resid` и top-k.
6. `n_floats = n_buckets + 2 + 2 * (число хранимых top-k пар)`.

## Ловушки

- Остаток делится на **полную ширину** бакета (вместе с позициями top-k значений) — так в
  оригинале; это даёт крошечный сдвиг, но сохраняет точную сумму по бакету.
- Значения выборки вне `[mn, mx]` (возможны под дрейфом, урок 8) — прижать к краям, иначе
  индекс бакета выйдет за массив. И подумать: что это делает с top-k на краю?
- В краевом бакете перебор словаря top-k — O(k); для k ≤ 20 это дешевле, чем сортированный массив.
