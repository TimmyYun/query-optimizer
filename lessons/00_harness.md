## Зачем

Прежде чем писать гистограммы, нужно точно понимать три вещи, на которых держится весь
эксперимент: что именно модель оценивает, откуда берётся правильный ответ и как мерить промах.
Ошибка на этом уровне (например, на единицу в границах) тихо портит **все** числа всех методов.

## Теория

### Задача

Перед выполнением `SELECT ... WHERE x BETWEEN a AND b` оптимизатор должен угадать, сколько
строк вернётся — **кардинальность**. От этого зависит план (какой join, индекс или full scan).
Посчитать честно = выполнить запрос, поэтому СУБД хранит сжатую **статистику** колонки и
оценивает по ней.

В проекте одна целочисленная колонка, домен `[0, 1_000_000]`, `N` = 60 млн строк (DSB — сотни тысяч).

### Что лежит в `meta.pkl`

```python
mn, mx, N, freq, sample, k, skew, kurt = pickle.load(open(".../meta.pkl", "rb"))
```

| поле | что это | кто может видеть |
|---|---|---|
| `mn, mx` | минимум и максимум колонки | модель (это метаданные каталога) |
| `N` | число строк | модель |
| `freq` | `freq[v - mn]` = сколько строк со значением `v`, длина `mx - mn + 1` | **только стенд** — это истина |
| `sample` | 100 000 случайных строк (reservoir sample, seed 42) | модель |
| `k` | число бакетов по Фридману–Диаконису: ширина `2·IQR / n^(1/3)` | модель |
| `skew, kurt` | асимметрия и эксцесс (для отчётов) | — |

Шаги дрейфа (`step_N.pkl`) — то же самое без `skew, kurt` (6 полей).

**Главное число курса: `N / len(sample)` = 600.** Одна точка выборки «представляет» 600 строк.
Всё, что в данных меньше ~600 строк, выборка может вообще не увидеть. Это потолок точности
для всех методов, которые строятся по выборке (все, кроме STHist).

### Ворклоады

| ворклоад | как сгенерирован | что проверяет |
|---|---|---|
| `workload_driven_1000000.csv` (по данным) | центр — случайная точка **выборки**, ширина 1–999 | реалистичные узкие запросы туда, где есть данные |
| `workload/1000000/narrow/workload.csv` (`@random`) | левая граница — равномерно по домену, ширина до 1000 | узкие запросы в любые места, включая пустые |
| `data/dsb/<col>/workload_driven_*.csv` | реальные запросы DSB (~1 400 уникальных, повторены) | реальная нагрузка |

Стенд берёт случайные 200 000 запросов (seed 42) и **выбрасывает запросы с истиной 0**
(как `load_and_filter_workload` в харнессе) — q-error для них не определён.

### Истина

Точный ответ на `[a, b]` через префиксные суммы — O(1) на запрос:

```
ps[i] = freq[0] + ... + freq[i-1],  ps[0] = 0
count(a, b) = ps[b - mn + 1] - ps[a - mn]      # обе границы ВКЛЮЧИТЕЛЬНО
```

Части запроса вне `[mn, mx]` дают 0 — индексы надо обрезать до `[0, len(freq)]`.

### Q-error

```
q_error = max(pred / true, true / pred),   pred и true прижимаются снизу к 1 строке
```

- симметричен: ошибиться вдвое вверх и вниз — одинаково плохо (для плана так и есть);
- **мультипликативный**: 10 vs 100 строк и 10 000 vs 100 000 — одна и та же ошибка ×10;
- прижатие к 1: «0 строк» и «0.3 строки» для оптимизатора одно и то же, без него q-error = ∞.

Смотрим **медиану** (типичный запрос) и **P95** (5% худших). Хвост важнее: плохие планы
рождаются там. Среднее почти бесполезно — его тянут единичные выбросы.

## Что написать

1. `estimators/__init__.py` — пустой.
2. `estimators/common.py`:
   - `RangeQuery(low, high)` — frozen dataclass;
   - `q_error(y_true, y_pred) -> np.ndarray` — векторно, с прижатием к 1;
   - `true_counts(freq, mn, lows, highs) -> np.ndarray` — префиксные суммы, без цикла по запросам;
   - `summarize(qe) -> dict` с ключами `median, p25, p75, p95, avg, max`.
3. `estimators/trivial.py` — **оценка без статистики**, точка отсчёта:
   ```python
   def build(sample, mn, mx, total_rows, n_buckets): ...
   # predict: total_rows * (длина пересечения [low, high] с [mn, mx]) / (mx - mn + 1)
   ```
   Это то, что делает СУБД, у которой нет гистограммы. Любой метод должен быть сильно лучше.

## Ловушки

- **Включительные границы.** `[5, 5]` — это одно значение, а не ноль. Ошибка на единицу
  в `true_counts` незаметна на широких запросах и катастрофична на точечных.
- **Запрос частично вне домена.** `[-100, 3]` при `mn = 0` — это `[0, 3]`, не ошибка.
- **`np.cumsum` по `int`** может переполниться на больших N — считай во `float64` или `int64`.
- Не тащи `freq` в модель «для удобства» — тогда результат эксперимента ничего не стоит.
