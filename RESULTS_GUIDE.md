# Как читать `results/all_results.xlsx`

Файл собирает `poetry run python export_results.py` из всех прогонов в
`results/`. Этот документ объясняет:

1. какой вопрос проверяет эксперимент и из каких частей он состоит;
2. что за методы стоят в строках;
3. что означает каждый лист и каждая колонка;
4. почему выбраны именно эти данные и запросы;
5. как правильно читать цифры и каких выводов из них делать нельзя.

**Сами результаты, их объяснение и вопросы научрука — в
[RESULTS_REPORT.md](RESULTS_REPORT.md).**

Как всё запустить — в [README.md](README.md). Общее устройство проекта — в
[PROJECT_GUIDE.md](PROJECT_GUIDE.md). Подробно о методах — в
[METHODS_EXPLAINED.md](METHODS_EXPLAINED.md).

## 1. Что проверяет эксперимент

**Исследовательский вопрос:** даёт ли модель распределения *внутри* бакета
гистограммы (Hybrid) более точную оценку кардинальности диапазонных запросов,
чем классические и самонастраивающиеся гистограммы при сопоставимых
затратах? И как это преимущество меняется, когда данные постепенно меняются (дрейф)?

На этот вопрос нельзя ответить одним датасетом. Ответ зависит от трёх
независимых факторов, и эксперимент варьирует каждый из них:

| Фактор | Варианты | Почему важен |
|---|---|---|
| **Форма данных** | 5 синтетических распределений × 2 варианта (`simple`, `hard`); реальные DSB и STATS-CEB | модель внутри бакета полезна только тогда, когда данные внутри бакета неравномерны |
| **Тип запросов** | узкие, широкие, data-driven; официальные запросы бенчмарков | у широкого запроса ошибка определяется суммой масс бакетов, у узкого — формой внутри бакета |
| **Изменение данных** | статика; дрейф через смешивание распределений; дрейф через официальные refresh-стримы DSB | проверяет, как быстро и какой ценой метод догоняет новые данные |

Каждый лист xlsx — одна комбинация этих факторов, то есть один *логический бенчмарк*.

## 2. Методы (строки таблиц)

Все методы получают **одинаковый вход**: сэмпл строк колонки и число бакетов
`k`. Ни один метод не видит точное распределение `freq`, из которого считается
правильный ответ. Методы с фидбэком дополнительно получают точные ответы на уже
выполненные запросы, как настоящий оптимизатор после выполнения запроса.

| Модель (колонка `Model`) | Что хранит | Как оценивает | Из чего строится | Роль в эксперименте |
|---|---|---|---|---|
| `EquiWidth` | `k` бакетов одинаковой ширины, в каждом число строк | равномерность внутри бакета | сэмпл | простейший базовый уровень |
| `EquiDepth` | бакеты с одинаковым числом строк + список самых частых значений (MCV) | MCV точно, остальное равномерно | сэмпл, как `ANALYZE` в PostgreSQL; бюджет `statistics_target = 100` | «что делает реальная СУБД» |
| `TKHist` | EquiWidth + точные частоты top-5 значений в каждом бакете | точные частоты для частых значений, равномерно для остальных | сэмпл | сильный базовый уровень на скошенных данных |
| `STHist` | бакеты, границы и массы которых подстраиваются по фидбэку | равномерность внутри бакета | **только** фидбэк запросов, данных не видит | самонастраивающаяся гистограмма |
| `EntropyHist-MEA` | границы бакетов выбраны по максимуму энтропии (вариант статьи) | непрерывная линейная интерполяция, как в статье | сэмпл | современная статическая гистограмма |
| `EntropyHist-MEA-Rng_discrete_linear` | та же гистограмма | интерполяция по целочисленным ячейкам (расширение, не из статьи) | сэмпл | показывает, сколько ошибки EntropyHist даёт сама формула оценки, а сколько — границы бакетов |
| **`Hybrid`** | EquiWidth-бакеты + маленькая модель CDF внутри каждого бакета (линейная, степенная, полином, дерево, изотоническая, MLP — выбирается по ошибке) | целые бакеты суммирует, в двух крайних бакетах применяет модель | сэмпл | **предлагаемый метод** |
| `EquiHist` | EquiWidth, массы которого масштабируются по фидбэку | равномерно | сэмпл + фидбэк | только при запуске с `--models EquiHist` (медленный) |

**Почему EntropyHist приводится дважды.** В статье доля бакета, попавшая в
запрос, считается как `перекрытие / (max − min)`. Если запрос задевает только
граничное значение бакета, перекрытие равно 0, и оценка тоже 0. На реальных
дискретных данных с пиком на границе это даёт катастрофические ошибки. На DSB:
`ws_wholesale_cost BETWEEN 100.00 AND 120.00` оценивается в 0 строк, а
правильный ответ — 19 440. Вариант статьи оставлен, потому что мы сравниваемся
со статьёй, а не с нашей правкой. Исправленный вариант приведён рядом, и разница
между двумя строками показывает вклад формулы оценки.

## 3. Листы

Порядок листов: `index` → `Выводы` → `Колонки` → по листу на каждый бенчмарк.
**Начинай с `Выводы`**, к листам с полными таблицами переходи за деталями.

### 3.1 Лист `index`

Здесь перечислены **все** бенчмарки из `registry.py`, в том числе те, что ещё
не запускались. Так сразу видно, чего в файле нет.

| Колонка | Смысл |
|---|---|
| `Лист` | имя листа с данными; пусто, если результатов нет |
| `Бенчмарк`, `Тип` | имя сценария и `static` / `drift` |
| `Что` | данные и запросы этого бенчмарка |
| `Папка` | откуда взяты результаты |
| `Статус` | `есть` / `не запускался` / `папка есть, результатов нет`. Последнее значит, что прогон не завершился |
| `Строк`, `Методы` | сколько строк и какие методы есть. Если метода не хватает, его прогон упал; смотри лог |
| `Как запустить` | команда, которая создаст этот лист |

### 3.1a Лист `Выводы`

Сводка обычным языком, в процентах ошибки, а не в q-error.
*Типичная ошибка* = (медиана q-error − 1) × 100 %, *ошибка худших 5 %* = (P95 − 1) × 100 %.

1. **Статика: кто лучший на каждом датасете.** Лучший метод по медиане и по
   хвосту (P95), ошибка и место Hybrid, число запросов. Колонка `Вывод`
   содержит готовую фразу, например «Лучший — TKHist (0.68 %); Hybrid на 2-м месте
   из 7 (0.77 %)». Если запросов меньше 50, это помечено как ненадёжное.
2. **Статика: общий рейтинг методов.** По каждому бенчмарку для каждого метода:
   средний ранг по датасетам, число побед, средние ошибки, время подготовки
   и время одной оценки в микросекундах. Отвечает на вопрос «какой метод
   лучше в целом на этом типе данных и чего это стоит».
3. **Дрейф: ошибка по всем шагам и стоимость адаптации.** Для каждой линии:
   средняя типичная ошибка по шагам, ошибка на последнем шаге, худший шаг,
   **сколько секунд адаптация заняла суммарно за шаги 1…S**, начальное
   построение и место. Строка `STHist_Online` помечена как несравнимая: она на другой половине запросов.

### 3.1b Лист `Колонки`

Глоссарий: каждая колонка всех листов с объяснением на русском.

### 3.2 Статические листы

| Лист | Данные | Запросы | На какой вопрос отвечает |
|---|---|---|---|
| `synth_simple_wide` | 5 гладких распределений | широкие (10–100 % домена) | контроль: здесь все методы должны быть близки к 1 |
| `synth_simple_narrow` | 5 гладких распределений | узкие (ширина до 1000) | помогает ли модель внутри бакета на гладких данных |
| `synth_hard_wide` | 5 распределений с локальными пиками и провалами | широкие | важна ли форма внутри бакета, когда запрос покрывает много бакетов |
| `synth_hard_narrow` | то же | узкие, равномерно по домену | основной случай для Hybrid: неравномерность внутри бакета + узкие запросы |
| `synth_hard_narrow_data_driven` | то же | узкие, центр берётся из данных | то же, но запросы идут туда, где есть данные, как в реальной нагрузке |
| `dsb_static` | DSB: `ws_wholesale_cost`, `ws_list_price` | официальные запросы DSB | реальные скошенные данные и реальные запросы |
| `stats_ceb_official` | STATS: 9 колонок `posts.*`, `users.*` | официальные однотабличные подзапросы STATS-CEB | реальные данные Stack Exchange и реальный workload |
| `stats_ceb_driven` | те же 9 колонок | **наш** data-driven workload, 100 000 запросов | статистически надёжная оценка на тех же данных; **не** запросы бенчмарка |

Одна строка — одна пара датасет × модель:

| Колонка | Смысл | Как читать |
|---|---|---|
| `Dataset` | распределение (синтетика) или колонка (`ws_list_price`, `users.UpVotes`) | |
| `Workload` | имя файла запросов | |
| `Model` | метод, см. раздел 2 | |
| `Queries` | сколько запросов участвует в оценке | запросы с правильным ответом 0 отбрасываются: q-error для них не определён. Поэтому число может отличаться между датасетами |
| `Median Q-Error` | медиана q-error | **основная метрика.** 1.00 — точно; 1.10 — типичная ошибка 10 %; 2.0 — в 2 раза |
| `P25 Q-Error`, `P75 Q-Error` | квартили | разброс «типичной» ошибки |
| `P95 Q-Error` | 95-й процентиль | хвост: насколько плохи худшие 5 % запросов. Для оптимизатора хвост часто важнее медианы, потому что плохой план выбирается именно на худших запросах |
| `Avg Q-Error` | среднее | чувствительно к единичным катастрофам. Если `Avg` намного больше `P95`, значит, есть несколько запросов с огромной ошибкой (пример — EntropyHist на DSB). Ищи причину, а не усредняй |
| `Build (s)` | время построения модели по сэмплу | для Hybrid сюда входит обучение моделей во всех бакетах |
| `Feedback Updates (s)` | время обучения по фидбэку | ненулевое только у STHist и EquiHist |
| `Train = Build + Updates (s)` | полная стоимость подготовки | сравнивай её между методами |
| `Inference, all queries (s)` | суммарное время всех вызовов `predict` | |
| `Inference / query, mean / median / p95 (s)` | время одной оценки | все методы замеряются одним циклом, на чистом Python. Абсолютные значения (микросекунды) отражают реализацию; сравнивай методы между собой |
| `Buckets` | число бакетов после построения | у EntropyHist это эффективное число, у STHist — после реструктуризаций; может быть меньше `k` |
| `Floats stored (Hybrid)` | сколько чисел хранят модели Hybrid | мера памяти. У гистограмм память примерно равна 2 × `Buckets` (+ top-k у TKHist, MCV у EquiDepth) |

Справа на листе — **сводная таблица медиан** (датасет × модель). С неё удобно начинать чтение.

### 3.3 Листы дрейфа

| Лист | Как меняются данные | Запросы |
|---|---|---|
| `drift_10_ds_zipf_wl_normal` | normal постепенно заменяется на zipf, шаг 10 % (11 шагов) | фиксированные, построены по normal |
| `drift_5_ds_zipf_wl_normal` | то же, шаг 5 % (21 шаг) | фиксированные, по normal |
| `drift_5_ds_zipf_wl_zipf` | то же | на каждом шаге свои, по текущим данным |
| `drift_5_ds_add_zipf_wl_zipf` | zipf **добавляется** к normal (только вставки, N растёт в 2 раза) | на каждом шаге свои |
| `dsb_drift_ws_wholesale_cost`, `dsb_drift_ws_list_price` | официальные refresh-стримы DSB: удаления по датам и вставки новых продаж | официальные запросы DSB, фиксированные |

*Почему именно такие сценарии.* Фиксированные запросы при меняющихся данных —
это нагрузка, которая не меняется, пока данные стареют (отчёты по расписанию).
Запросы, которые меняются вместе с данными, — пользователи спрашивают о новом.
Замена и добавление — два основных способа, которыми таблица меняется на практике.
DSB даёт настоящий механизм изменений бенчмарка, а не наше смешивание.

Одна строка — один шаг × модель × стадия:

| Колонка | Смысл |
|---|---|
| `Run` | префикс прогона, например `gradual_ws_list_price_to_refresh` |
| `Drift %` | синтетика: доля целевого распределения в смеси. DSB: накопленный churn, то есть (удалённые + вставленные строки) / исходное число строк |
| `Step` | имя чекпоинта DSB (`initial`, `churn_5pct` …); у синтетики пусто |
| `Model`, `Stage` | метод и стадия адаптации |
| `Line` | `Model_Stage`, имя линии на графике |
| `Median / P95 / Avg Q-Error` | как на статических листах, **на eval-половине запросов** |
| `Inference / query, median / mean (s)` | время одной оценки |
| `Adaptation cost at this step (s)` | сколько секунд модель потратила **на этом шаге**, чтобы оказаться в этой стадии, с накоплением внутри шага. Гистограммы: пересборка по сэмплу (`ANALYZE`). Hybrid: `Shock` = обновление масс бакетов по сэмплу, `FT` = + подстройка по фидбэку, `RB` = + переобучение бакетов. STHist: обучение по фидбэку. `EntropyHist_Static`: 0 |
| `Rebuilt buckets` | только `Hybrid_RB`: сколько бакетов переобучено на шаге |
| `Initial build, step 0 (s)` | построение модели на шаге 0 (у Hybrid — обучение всех моделей); в стоимость стадий не входит |

Справа — медиана по шагам (`Drift %` × `Line`).

**Как читать стоимость.** Метод, который всё время пересобирается (TKHist,
EquiDepth), платит за каждый шаг. Hybrid платит один раз и дорого (начальное
обучение), а дальше дёшево, если переобучает мало бакетов. Чтобы сравнить
полную цену, сложи `Начальное построение` и `Адаптация за все шаги` на листе
`Выводы`. Обновление масс у Hybrid (стадия Shock) замеряется только в прогонах
после этого изменения; в старых результатах там 0.

**Стадии.** Как метод реагирует на изменения:

| `Line` | Что сделано к моменту оценки | Что показывает |
|---|---|---|
| `EquiWidth`, `EquiDepth`, `TKHist` | гистограмма пересобрана по сэмплу шага (`ANALYZE`) | стандартная практика СУБД — обновить статистику |
| `EntropyHist-*_Static` | гистограмма шага 0, без изменений | сколько стоит **не** обновлять статистику |
| `EntropyHist-*_Rebuild` | пересобрана по сэмплу шага | то же, что `ANALYZE` |
| `Hybrid_Shock` | массы бакетов обновлены по сэмплу, модели внутри бакетов старые | дешёвое обновление Hybrid |
| `Hybrid_FT` | + массы бакетов подстроены по фидбэку adapt-половины | добавляет ли что-то фидбэк поверх `ANALYZE` |
| `Hybrid_RB` | + переобучены бакеты, где медианная ошибка на adapt-половине > 1.3 | полная адаптация Hybrid |
| `STHist_Shock` | гистограмма прошлого шага, без фидбэка этого шага | реакция на изменения без обучения |
| `STHist_Online` | prequential по adapt-половине: оценка, затем обучение | **единственная линия на другой половине запросов**, напрямую с остальными не сравнивается |
| `STHist_Post` | после обучения на adapt-половине | итог адаптации по фидбэку |

## 4. Почему именно эти данные и запросы

### 4.1 Синтетика

- **60 млн строк, домен [0, 1 000 000].** Таблица настолько большая, что сэмпл в
  100 тыс. строк — это 0.17 % данных, как у настоящей `ANALYZE`. Домен достаточно
  широк, чтобы бакеты были содержательными.
- **Пять распределений** покрывают типовые формы: равномерное (контроль),
  нормальное (один пик), zipf (длинный хвост), anti-zipf (масса справа),
  sparse_cluster (кластеры с пустотами).
- **`simple` против `hard`.** На гладких данных внутри бакета почти равномерно,
  и любая гистограмма почти идеальна. `hard` добавляет локальные пики и провалы,
  то есть ровно ту неравномерность внутри бакета, ради которой создан Hybrid.
  Сравнение двух вариантов отделяет эффект метода от эффекта данных.

### 4.2 DSB

- **Почему DSB:** это TPC-DS со специально скошенными распределениями и
  механизмом обновлений. Стандарт де-факто для аналитических нагрузок.
- **Почему `web_sales.ws_wholesale_cost` и `ws_list_price`.** В официальных
  шаблонах DSB только по этим колонкам `web_sales` есть одномерные диапазоны
  вида `col BETWEEN a AND b`: 8 и 9 шаблонов. Официальные refresh-стримы меняют
  именно `web_sales`. Значит, и данные, и запросы, и изменения берутся из самого
  бенчмарка. Суррогатные ключи (`*_item_sk`), которые использовались раньше,
  в официальных запросах встречаются только в соединениях; диапазоны по ним
  были бы нашей выдумкой.
- **Как взяты запросы:** `dsqgen` на неизменённых шаблонах, той же командой, что
  и официальный генератор, 1000 экземпляров на шаблон, seed 42. Из каждого запроса
  берётся одномерный предикат по колонке. Дубликаты убраны: каждый различный
  диапазон считается один раз. Получилось 261 и 985 запросов.
- **Цены в центах.** DECIMAL(7,2) хранится как целое ×100. Границы запросов
  масштабируются так же, поэтому ответы не меняются.
- **Особенность:** у `ws_wholesale_cost` в базовых данных ровно 20 различных
  значений. Методы, которые хранят частоты отдельных значений (TKHist, EntropyHist),
  на статике дают почти идеальный и одинаковый результат. После дрейфа значений
  становится больше 1000, и данные становятся сложнее. Поэтому **дрейф DSB
  информативнее статики DSB.**

### 4.3 STATS-CEB

- **Почему STATS-CEB:** это реальная база Stack Exchange и реальный workload из
  современного бенчмарка оценки кардинальности (Han et al., VLDB 2022).
- **Почему 9 колонок.** Это все целочисленные колонки, по которым в официальных
  однотабличных подзапросах есть хотя бы 8 различных диапазонов. Таймстемпы
  исключены: секундное разрешение не помещается в плотный массив частот.
- **Проверка:** наш расчёт правильного ответа совпадает с кардинальностями из
  официального файла в 48 случаях из 48.
- **Сэмпл 30 000 строк**, как `ANALYZE` в PostgreSQL. Таблицы маленькие
  (40–92 тыс. строк), и стандартный сэмпл в 100 тыс. содержал бы всю колонку.
- **Два листа.** `stats_ceb_official` — честный результат на запросах бенчмарка,
  но их всего 8–33 на колонку. `stats_ceb_driven` — 100 000 наших запросов на тех
  же данных, ради статистической надёжности. Это **два разных результата**:
  их нельзя объединять, а второй нельзя называть результатом STATS-CEB.

## 5. Как читать цифры

**Порядок чтения листа:**
1. Открой сводную таблицу медиан справа и найди лучший метод по каждому датасету.
2. Проверь `P95 Q-Error`. Метод с хорошей медианой и плохим хвостом опасен для оптимизатора.
3. Сравни `Avg Q-Error` с `P95`. Большой разрыв означает отдельные катастрофы. Найди их причину (раздел 6), не усредняй их молча.
4. Сопоставь точность со стоимостью: `Train … (s)`, `Inference / query`, `Floats stored`.
5. Посмотри `Queries`: при 10–30 запросах различия во втором знаке случайны.

**Масштаб q-error.** 1.00–1.05 — практически точно. 1.05–1.5 — хорошо.
1.5–2 — заметная ошибка. Больше 2 — плохо для выбора плана. Сравнивай отношения:
медиана 1.02 против 1.04 — это двукратная разница в *отклонении* от идеала,
хотя абсолютные числа близки.

**Что говорит в пользу Hybrid** (если наблюдается):
- выигрыш на `synth_hard_*` и `*_narrow*` при отсутствии выигрыша на `synth_simple_wide`
  — это ровно то поведение, которое предсказывает идея метода;
- в дрейфе: `Hybrid_RB` ближе к 1, чем пересобранные гистограммы, при меньшей стоимости шага.

**Каких выводов делать нельзя:**
- нельзя сравнивать числа с прогонами до исправлений (`PROJECT_GUIDE.md`, раздел 9);
- нельзя сравнивать `STHist_Online` с остальными линиями дрейфа: другая половина запросов;
- нельзя считать абсолютное время в микросекундах характеристикой метода в СУБД: это Python-реализация;
- нельзя объединять `stats_ceb_official` и `stats_ceb_driven`;
- статика `ws_wholesale_cost` почти ничего не говорит о методах: там 20 значений.

## 7. Сводка решений

| Решение | Альтернатива | Почему выбрано это |
|---|---|---|
| модели строятся только по сэмплу | строить по точному распределению | так работает реальная СУБД; иначе задача нечестно упрощается |
| одна функция правильного ответа и один цикл оценки | у каждого метода свой код | одинаковые правила для всех; раньше копии расходились |
| одинаковое число бакетов `k` (кроме EquiDepth) | у каждого метода своё | сравнение при равном бюджете; EquiDepth следует PostgreSQL |
| prequential для методов с фидбэком | учиться и оценивать на одном запросе | модель не должна видеть ответ до оценки |
| в дрейфе adapt- и eval-половины | адаптация и оценка на одних запросах | иначе адаптация оценивается на обучающей выборке |
| официальные запросы DSB и STATS-CEB | генерировать свои запросы | результат должен относиться к бенчмарку, а не к нашему генератору |
| колонки DSB с официальными диапазонами | суррогатные ключи | диапазонов по ключам в бенчмарке нет |
| сэмпл 30 000 на STATS-CEB | 100 000, как у синтетики | таблицы меньше 100 000 строк; 30 000 — значение PostgreSQL |
| два варианта EntropyHist | только вариант статьи / только исправленный | сохранить сравнение со статьёй и показать вклад формулы оценки |
| отдельный лист `stats_ceb_driven` | только официальные запросы | 8–33 запроса мало для надёжных процентилей, но смешивать нельзя |
| удаление дубликатов запросов | оставлять повторы | повтор одного диапазона не несёт новой информации и искажает процентили |
