Этот документ для того, кто впервые открыл репозиторий. Он объясняет, что
измеряет бенчмарк, почему он устроен именно так, как всё запустить с нуля
и как читать результаты.

- Полный список команд и параметров — в [README.md](README.md).
- Как работает каждый метод — в [METHODS_EXPLAINED.md](METHODS_EXPLAINED.md).
- Как читать таблицу результатов `all_results.xlsx` — в [RESULTS_GUIDE.md](RESULTS_GUIDE.md).

## 1. Задача

Оптимизатор запросов СУБД выбирает план выполнения по **оценке кардинальности**:
сколько строк вернёт предикат `WHERE col BETWEEN low AND high`. Ошибка оценки в
10 раз легко превращает быстрый план в медленный. Поэтому оценку держат в
компактной структуре, чаще всего в гистограмме, и обновляют по сэмплу данных.

Проект сравнивает несколько таких структур на **одной целочисленной колонке**:

| Метод | Идея | Откуда |
|---|---|---|
| EquiWidth | бакеты одинаковой ширины | учебник |
| EquiDepth | бакеты одинаковой глубины + MCV, как `ANALYZE` в PostgreSQL | PostgreSQL |
| TKHist | EquiWidth + точные частоты top-k значений в каждом бакете | DHist |
| STHist | гистограмма, которая учится только на фидбэке запросов | Aboulnaga & Chaudhuri, SIGMOD 1999 |
| EntropyHist | границы бакетов по максимуму энтропии | To, Chiang & Shahabi, CIKM 2013 |
| **Hybrid** | EquiWidth-бакеты + маленькая модель CDF внутри каждого бакета | **предлагаемый метод** |
| Equi-Hist | онлайн-масштабирование бакетов по фидбэку | не входит в основной дизайн: слишком медленный |

**Метрика — q-error**: `max(оценка/истина, истина/оценка) ≥ 1`. Значение 1 —
идеальная оценка, 2 — ошибка в 2 раза в любую сторону. Мы сообщаем медиану,
p25, p75, p95 и среднее. Среднее чувствительно к единичным катастрофам, медиана нет.
Поэтому смотреть нужно на обе.

## 2. Принципы методологии и почему они такие

Каждый принцип защищает от конкретного способа получить нечестный результат.

### 2.1 Модель никогда не видит истину

Для каждого датасета хранится кортеж `meta.pkl = (mn, mx, N, freq, sample, k, skew, kurt)`:

- `freq` — точная частота каждого значения. Используется **только** чтобы посчитать правильный ответ;
- `sample` — случайная выборка. **Только** из неё модели строятся, с масштабом `N / len(sample)`.

*Почему.* Настоящая СУБД не знает точного распределения, у неё есть только
`ANALYZE`-сэмпл. Модель, построенная по `freq`, решала бы другую, более лёгкую
задачу. Методы с фидбэком (STHist, Equi-Hist, Hybrid-FT) дополнительно получают
точный ответ на **уже выполненные** запросы, как его получил бы настоящий оптимизатор.

### 2.2 Истина считается одной функцией

`benchmark_utils.exact_counts` — единственное место, где вычисляется правильный
ответ. Им пользуются статика, дрейф и адаптеры бенчмарков.

*Почему.* Раньше в каждом раннере была своя копия формулы. В копиях для дрейфа
запрос целиком вне домена получал ненулевую истину, а фильтрация шла со
сдвигом на `mn`. Одна функция с тестом против перебора убирает этот класс ошибок.

Запросы с истиной 0 отбрасываются: q-error для них не определён. Оценка и истина
перед q-error ограничиваются снизу одной строкой.

### 2.3 Один цикл оценки для всех методов

`benchmark_utils.run_queries` / `evaluate_and_save`. Раннер только строит модель
и передаёт `predict` (и `feedback` для методов с обучением). Таймер измеряет
только вызов `predict`. Время обучения по фидбэку считается отдельно.

*Почему.* Раньше каждый раннер замерял время по-своему: где-то это была сумма
вызовов `predict`, где-то время всего цикла вместе с накладными расходами.
Сравнивать время методов было нельзя, а колонка Train в сводной таблице
у пяти методов из шести была пустой из-за разных ключей.

### 2.4 Методы с обучением оцениваются prequential

Для статических запусков STHist и Equi-Hist запрос сначала оценивается, и только
потом модель учится на его ответе. Иначе модель оценивалась бы на запросе, ответ
на который уже видела.

### 2.5 В дрейфе: адаптация на одной половине запросов, оценка на другой

Запросы каждого шага один раз делятся пополам (`split_adapt_eval`, seed 42):

- **adapt** — только по фидбэку этих запросов можно учиться (Hybrid FT/RB, STHist, Equi-Hist);
- **eval** — на них оцениваются **все стадии всех моделей**.

*Почему.* Раньше Hybrid-FT подстраивался по фидбэку тех же запросов, на которых
его потом мерили. Это оценка на обучающей выборке, и она завышает качество
адаптации. Методы с `ANALYZE` такого преимущества не имели. Теперь все стадии
всех моделей меряются на одних и тех же запросах, которые модели не видели.
При фиксированном workload разбиение одинаково на всех шагах, так что
eval-запрос не выучивается ни на одном шаге.

### 2.6 Одинаковый бюджет

По умолчанию все методы, кроме EquiDepth, получают одно число бакетов `k`
(правило Фридмана–Диакониса по сэмплу). EquiDepth следует PostgreSQL и берёт
`statistics_target` = 100. Бакеты — это ещё не память: TKHist хранит top-k
значений, Hybrid — модели (`n_floats`). Для честного сравнения по памяти
есть `run_hybrid_ablations.py --part memory`.

### 2.7 Воспроизводимость

Все генераторы используют seed 42: данные, сэмплы, workload, обучение моделей,
`dsqgen -rngseed`. Hybrid обучает бакеты в потоках, поэтому seed каждого бакета
фиксируется заранее и от порядка потоков не зависит. Внешние бенчмарки
закреплены на коммитах: DSB `ec9a156`, STATS-CEB `670cb8d`.

## 3. Данные

### 3.1 Синтетика

60 млн строк, домен `[0, 1 000 000]`, пять распределений: `normal`, `zipf`,
`anti_zipf`, `uniform`, `sparse_cluster`. Каждое в двух вариантах:

- `simple` — чистое распределение;
- `hard` — с вкраплениями локальных пиков и провалов (micro-distributions).

*Почему два варианта.* На гладких данных внутри бакета почти равномерно, и
равномерная интерполяция гистограммы уже близка к идеалу. `hard` специально
делает данные внутри бакета неравномерными. Именно здесь видно, приносит ли
пользу модель внутри бакета у Hybrid.

### 3.2 Дрейф синтетики

Последовательность `step_0 … step_S` смешивает начальное распределение `I`
(normal) с целевым `T` (zipf):

- `replace`: `(1 − a)·I + a·T` — данные постепенно заменяются, N постоянно;
- `add`: `I + a·T` — новые данные добавляются поверх старых, N растёт до 2×.

Это два реальных сценария: обновление таблицы и рост таблицы вставками.

### 3.3 Workload

| Тип | Как строится | Зачем |
|---|---|---|
| narrow | случайный центр, ширина до 1000 | точечные и узкие запросы, где важна форма внутри бакета |
| wide | случайный центр, ширина 10–100 % домена | широкие запросы, где важна в основном суммарная масса бакетов |
| data-driven | центр берётся из сэмпла данных | запросы туда, где есть данные; ближе к реальной нагрузке |

Вывод прошлых прогонов: вид workload влияет на ранжирование методов сильнее,
чем форма данных. Поэтому workload — отдельное измерение эксперимента.

### 3.4 DSB (реальные данные, дрейф через официальные обновления)

[DSB](https://github.com/microsoft/dsb) — это TPC-DS со скошенными данными.

**Колонки: `web_sales.ws_wholesale_cost` и `web_sales.ws_list_price`.**
Почему именно они:
- в официальных шаблонах запросов DSB только по этим колонкам `web_sales` есть
  настоящие одномерные диапазоны `col BETWEEN a AND b`. По суррогатным ключам
  (`*_item_sk`) диапазонов там нет, они встречаются только в соединениях;
- официальные refresh-стримы меняют именно `web_sales`, поэтому дрейф идёт
  через механизм самого бенчмарка.

Цены имеют тип DECIMAL(7,2) и хранятся в целых центах (×100). Границы запросов
масштабируются так же, так что преобразование без потерь.

**Запросы** генерирует `dsqgen` по неизменённым официальным шаблонам той же
командой, что и официальный `scripts/generate_workload.py`. Из каждого запроса
берутся одномерные предикаты по колонке. Предикаты на отношение колонок
(`ws_sales_price / ws_list_price BETWEEN …`) одномерными не являются и
отбрасываются. Получилось 261 и 985 различных диапазонов.

**Дрейф.** Ноутбук `DSB_GENERATOR.ipynb` применяет официальные refresh-стримы
(удаления по диапазонам дат, вставки по staging-файлам) и сохраняет колонку на
каждых 5 % накопленного churn. Получается 21 шаг.

Что важно знать о данных DSB:
- у `ws_wholesale_cost` в базовых данных **ровно 20 различных значений**,
  у `ws_list_price` — 397. Методы, которые хранят частоты отдельных значений
  (TKHist, EntropyHist), на статике `ws_wholesale_cost` дают одинаковый
  почти идеальный результат: это ожидаемо, а не баг;
- после refresh различных значений становится больше 1 000: вставки берут
  цену текущей версии товара (`i_wholesale_cost`), и там встречаются значения
  меньше 1.00 $. Это и есть дрейф распределения;
- в таблице `item` у нескольких товаров цена NULL. Раньше ноутбук превращал её
  в 0.00 (`fillna(0)`), и в данных появлялись строки с нулевой ценой. Сейчас
  NULL остаётся NULL, как в SQL, и в колонку не попадает.

### 3.5 STATS-CEB (реальные данные и реальные запросы)

[STATS-CEB](https://github.com/Nathaniel-Han/End-to-End-CardEst-Benchmark):
данные Stack Exchange и workload CEB. Берутся официальные
`stats_simplified/{posts,users}.csv` и
`stats_CEB_single_table_sub_query.sql`. В каждом однотабличном подзапросе
предикаты по одной колонке пересекаются в один диапазон. Используется
9 целочисленных колонок. Колонки-таймстемпы исключены: секундное разрешение
не помещается в плотный массив `freq`.

**Проверка адаптера:** у одномерных подзапросов в официальном файле записана
кардинальность, и наш расчёт совпадает с ней в 48 случаях из 48.

**Сэмпл 30 000 строк**, как у `ANALYZE` в PostgreSQL (300 × 100). В таблицах
всего 40–92 тыс. строк. Со стандартным для синтетики сэмплом в 100 тыс. модели
получили бы всю колонку целиком, и задача стала бы тривиальной.

**Ограничение:** в официальном workload всего 8–33 различных диапазона на
колонку, поэтому p95 по ним статистически ненадёжен. Для статистической мощности
есть отдельный эксперимент `stats_ceb_driven`: 100 тыс. запросов нашего
генератора на тех же официальных данных. Это **не** запросы бенчмарка, и в
статье его нужно приводить отдельно.

## 4. Как устроен код

```text
           источник данных                     адаптер                        контракт
синтетика: data/datasets.py, generate_shifts.py ───────────────► meta.pkl / step_N.pkl
DSB:       setup_dsb.sh → DSB_GENERATOR.ipynb ─► prepare_benchmark.py ─► + workload_official.csv
STATS-CEB: скачивание (закреплённый коммит) ───► prepare_benchmark.py ─►
workload:  workload/workload.py ───────────────────────────────► workload_*.csv

registry.py ──► run_experiments.py / run_drift_experiments.py ──► run_<model>[_drift].py
                                                                      │
                     benchmark_utils: exact_counts, run_queries, split_adapt_eval
                                                                      ▼
                                                 results/<experiment>/...
                                                                      │
                              merge_drift.py, plot_drift.py, export_results.py
```

| Файл | Роль |
|---|---|
| `models/*.py` | сами методы; общий интерфейс `predict(q)` возвращает число строк |
| `run_<model>.py` | статический раннер: строит модель и отдаёт её в общий цикл |
| `run_<model>_drift.py` | дрейф: цикл по шагам и стадии модели |
| `benchmark_utils.py` | истина, общий цикл оценки, разбиение adapt/eval, сохранение результатов |
| `registry.py` | **единственный** список методов и сценариев |
| `prepare_benchmark.py` | адаптер DSB и STATS-CEB к контракту `meta.pkl` |
| `merge_drift.py`, `plot_drift.py` | сводные таблицы и графики дрейфа |
| `export_results.py` | все результаты в один xlsx |
| `setup_env.sh`, `DSB benchmark/setup_dsb.sh` | установка с нуля |
| `run_sthist_paper.py`, `run_entropyhist_paper.py` | воспроизведение экспериментов из исходных статей (отдельно от бенчмарка) |
| `run_hybrid_ablations.py` | абляции Hybrid и сравнение при равной памяти |
| `plot/` | вспомогательные графики workload и распределений |
| `tests/` | юнит-тесты: harness, адаптеры, STHist, EntropyHist |

## 5. Запуск с нуля

Порядок команд. Время указано ориентировочно.

```bash
./setup_env.sh                       # окружение + синтетические workload + STATS-CEB   (~10 мин)
poetry run pytest -q                 # всё должно быть зелёным

# статические эксперименты
poetry run python run_experiments.py --scenario all              # синтетика + STATS-CEB (+ DSB, если подготовлен)

# дрейф синтетики (долго: часы)
poetry run python run_drift_experiments.py --scenario drift_5_ds_zipf_wl_normal

# DSB: один раз собрать тулкит и данные (часы), потом эксперименты
"DSB benchmark/setup_dsb.sh"
./setup_env.sh --dsb
poetry run python run_experiments.py --scenario dsb
poetry run python run_drift_experiments.py --scenario dsb_drift_ws_wholesale_cost
poetry run python run_drift_experiments.py --scenario dsb_drift_ws_list_price

# результаты
poetry run python merge_drift.py --experiment-name dsb_drift_ws_wholesale_cost dsb_drift_ws_list_price
poetry run python plot_drift.py  --experiment-name dsb_drift_ws_wholesale_cost dsb_drift_ws_list_price
poetry run python export_results.py          # results/all_results.xlsx
```

Полезные флаги оркестраторов:
- `--models EquiWidth Hybrid` — запустить только эти модели;
- `--dry-run` — только напечатать команды.

**Перед повторным прогоном эксперимента удаляй его папку в `results/`.**
Сводная таблица собирает все `summary_*.json` из папки, и старые файлы
попадут в неё вместе с новыми.

## 6. Как читать результаты

`results/all_results.xlsx`:

- лист `index` — что лежит на каждом листе;
- статический лист — строка на пару датасет × модель: q-error, время построения
  и обучения, время одного `predict`, число бакетов; справа сводная таблица медиан;
- лист дрейфа — строка на шаг × модель × стадию; справа медиана по шагам.

Стадии дрейфа:

| Линия | Что это |
|---|---|
| `EquiWidth`, `EquiDepth`, `TKHist` | после `ANALYZE` (пересборка по сэмплу шага) |
| `Hybrid_Shock` | счётчики бакетов обновлены по сэмплу, модели внутри бакетов старые |
| `Hybrid_FT` | плюс подстройка масс бакетов по фидбэку adapt-половины |
| `Hybrid_RB` | плюс переобучение плохих бакетов |
| `STHist_Shock` / `_Online` / `_Post` | до фидбэка шага / prequential по adapt-половине / после фидбэка |
| `EntropyHist-*_Static` / `_Rebuild` | гистограмма шага 0 / пересобранная по сэмплу шага |

Сравнивать нужно линии на одной eval-половине: все, кроме `STHist_Online`.

## 7. Известные особенности (не баги, но о них нужно писать)

1. **EntropyHist на дискретных данных.** Оценка из статьи (`paper_linear`)
   непрерывна: если запрос задевает только граничное значение бакета, оценка
   равна 0. На дрейфе к zipf это даёт среднюю q-error 242–446 при медиане
   около 1.1 (вариант `discrete_linear`: 1.35–1.44).
   Поэтому есть второй вариант `EntropyHist-MEA-Rng_discrete_linear`, который
   считает по целочисленным ячейкам. Приводятся оба.
2. **EquiWidth при IQR = 0.** У `users.UpVotes` и `users.DownVotes` больше
   половины строк равны 0, межквартильный размах нулевой, и правило
   Фридмана–Диакониса возвращается к 10 бакетам. Отсюда q-error 16–20 у
   EquiWidth. Это свойство правила выбора `k`, а не метода.
3. **Hybrid FT может ухудшать результат по сравнению с Shock** (подтверждено
   и после разбиения adapt/eval): на DSB `ws_wholesale_cost` 1.008 → 1.015, на
   последнем шаге дрейфа к zipf 22 → 66. Массы бакетов уже пересчитаны по
   сэмплу, и масштабирование всего бакета по ошибке отдельных запросов сдвигает
   верную массу. RB это исправляет. Подробно — `RESULTS_REPORT.md`, раздел 4.4.
4. **Мало официальных запросов STATS-CEB** (раздел 3.5).

## 8. Как расширять

**Новый метод:**
1. `models/<name>.py`: строится только из `sample`, `predict(q)` возвращает число строк. После изменения счётчиков вызывай `_bake_vectorized_data()`.
2. `run_<name>.py` по образцу `run_tkhist.py`: построить модель и вызвать `evaluate_and_save`.
3. `run_<name>_drift.py` по образцу `run_tkhist_drift.py`, с `split_adapt_eval`.
4. Одна строка в `MODELS` в `registry.py`. Вариант того же метода — та же строка с `"args": [...]`.
5. Тест в `tests/`.

**Новый бенчмарк:** функция в `prepare_benchmark.py`, которая из **неизменённых**
данных и запросов бенчмарка пишет `meta.pkl` и `workload_official.csv`. Затем
одна запись в `STATIC_SCENARIOS`. Для дрейфа — `drift/step_N.pkl` и запись в
`DRIFT_SCENARIOS`.

| Что было | Последствие | Исправление |
|---|---|---|
